# pipeline-design

# Autoencoder Pipeline — Design Document

Pipeline: `ingest → preprocess → segment regimes → filter dropout/transient → clean (per regime) → split → train → calibrate thresholds -> save artefacts → infer & diagnose (heuristic) → alert → monitor (unwired) → evaluate (offline)`

## 1. Ingestion & Preprocessing

| Step | When | What (feature) | Why it exists | How  | What if not |
| --- | --- | --- | --- | --- | --- |
| **Data loading & schema validation** | At pipeline start, when `step_clean` is invoked with a raw sensor data file (CSV or Parquet, local path or S3 URI) | Loads the file, auto-detecting format from extension, parses and time-sorts the timestamp column, auto-detects sensor columns (all numeric columns except timestamp/exclusions), and validates the schema before any numeric processing begins | Fail fast on a malformed or unexpected schema rather than letting a bad column reach the scaler or model; `read_parquet_robust` exists specifically to work around a real pyarrow limitation (“a wide table containing large list<…> columns can fail to convert to pandas in one shot … Observed on a real export with list columns … that grew large enough per-row (up to ~1,884 concurrent entries on one equipment)”) | `load_data` picks `pd.read_csv`/`pd.read_parquet` by suffix, then `pd.to_datetime` + `sort_values`/`reset_index` on the timestamp column. `detect_sensor_columns` keeps columns that are `pd.api.types.is_numeric_dtype` and not timestamp/excluded, returned sorted. `validate_dataframe` checks for a missing timestamp column, missing expected sensors, and non-numeric sensor columns, returning an error list that `main.py` treats as fatal (`sys.exit(1)`). `read_parquet_robust` reads scalar columns normally and any list-typed columns separately, chunk by chunk, then reassembles. `load_data` (`ingestion.py`), `detect_sensor_columns` (`ingestion.py`), `validate_dataframe` (`ingestion.py`), `read_parquet_robust` (`ingestion.py`) | Without timestamp sorting, `construct_windows` would slice non-chronological blocks and every downstream time-dependent step (regime segmentation, threshold history) would operate on scrambled order. Without validation, a stray non-numeric column (e.g. a text status tag) would reach `fit_robust_scaler`/`RobustScaler.fit` and crash with an opaque dtype error instead of a clear “Non-numeric sensor columns” message at load time. Without the chunked parquet workaround, any wide historian export with large list-typed columns would raise `ArrowNotImplementedError` and fail to load at all |
| **Low-variance / constant column removal** | After sensor columns are detected, before the scaler is fit; evaluated per sensor column against `preprocessing.variance_threshold` (default `1e-5`) | Drops sensor columns whose variance is at or below the threshold — constant or near-constant tags | Per docstring: “Constant or near-constant sensors (e.g. boolean run-status, stuck sensors) add noise to the autoencoder without useful signal. This step drops them before training” | Computes `df[sensor_columns].var(numeric_only=True)`, selects columns with `variance <= variance_threshold` as `removed_columns`, and returns the complement as `kept_columns` alongside a full per-column variance dict for auditing. `remove_low_variance_columns` (`preprocessing.py`); variance computation `preprocessing.py`; threshold filter `preprocessing.py` | A boolean run-status or stuck sensor left in would contribute zero reconstruction signal while still occupying a model input dimension, diluting capacity across sensors that matter. A near-constant tag just above the threshold (tiny but nonzero IQR) that slips through would, per `apply_scaling`’s own rationale for IQR-degenerate tags, get divided by a near-zero IQR under `RobustScaler` and any small fluctuation would rescale to an outsized z-score, swamping the MSE loss the same way an uncompressed glitch does. Set the threshold too high (as the test does at `1e6`) and every sensor column is stripped, leaving nothing for the autoencoder to model |
| **RobustScaler fit restricted to train-portion slice** | After low-variance filtering, on the finalized `sensor_columns`; fit once, on a chronological head-slice of the full time-sorted dataframe sized by `training.splits.train` (default 0.85), before windowing, regime segmentation, or cleaning | Fits a single `sklearn.preprocessing.RobustScaler` (median/IQR) on only the earliest `n_train_rows = int(len(df) * train_pct)` rows, then reuses that frozen scaler for the entire dataset and at inference | Reduce the effect of outliers in the training data, specifically using median and IQR rather than mean-based scaling to better handle skewed distributions.  | `fit_robust_scaler` calls `RobustScaler().fit(df[sensor_columns].values)`, exposing `scaler.center_` (median) and `scaler.scale_` (IQR) as `medians`/`iqrs`. `main.py` computes `n_train_rows` from `train_pct` and calls `fit_robust_scaler(df.iloc[:n_train_rows], sensor_columns)` before any windowing occurs. `fit_robust_scaler` (`preprocessing.py`); slice/fit call `main.py`; leakage-avoidance comment `main.py` | Fitting on the full dataset (including future val/test rows) leaks distribution information into the median/IQR estimate, producing an optimistic reconstruction-error baseline that undermines the later val/test evaluation split. Fitting per-regime or per-window instead of once up front would let each window locally re-normalize its own anomalies away. Refitting the scaler on live inference data would let a developing fault’s own drift shift the median/IQR, silently absorbing the anomaly into the “normal” band instead of flagging it |
| **Scaling application + tail compression** | Applied to the entire time-sorted dataframe (not just the train slice) using the scaler fit in the previous step; tail compression (`c*asinh(z/c)`) is applied only when `preprocessing.tail_compression_scale` is set to a non-null value in config (left `null` by default) | Transforms every sensor column via `(x - median) / IQR`; if a compression scale `c` is configured, additionally passes the result through the generalized inverse hyperbolic sine transform | Per `apply_scaling` docstring: RobustScaler “divides by the interquartile range, which is near-zero for tags that sit in a narrow band almost all the time (deadband-logged sensors, gas-composition fractions, analyzer-fault readings).” A glitch on such a tag — “confirmed on real historian data as a correlated event, tens of tags spiking together at one timestamp” — “rescales to a z-score in the thousands or more, which swamps the MSE loss.” `asinh(x)` behaves like `x` for `\|x\| << c` and like a log for `\|x\| >> c`, so “relative severity, and the gradient, are preserved instead of saturating to a flat zero-gradient plateau” the way a hard clip would.  | `apply_scaling` calls `scaler_result.scaler.transform(df[sensor_columns].values)` then `apply_tail_compression`. `apply_tail_compression` is a no-op when `tail_compression_scale is None`, else returns `c * np.arcsinh(scaled_values / c)`; split out from `apply_scaling` so a single raw inference window already run through `scaler.transform()` can get the identical transform the model was calibrated with. `apply_scaling` (`preprocessing.py`), transform+compression calls `preprocessing.py`; `apply_tail_compression` (`preprocessing.py`) | Without tail compression, a correlated glitch across many IQR-degenerate tags rescales to z-scores in the thousands-plus, swamping MSE loss so the autoencoder “learns nothing from the other (well-behaved) sensors.” Hard-clipping instead of `asinh` saturates the gradient to a flat plateau, making a mild 100-sigma glitch indistinguishable from a 2e9-sigma one (test `test_tail_compression_preserves_relative_ordering` checks severe > mild is preserved). Dropping the offending rows/windows instead of compressing them would break the requirement that “a timestamp can’t simply be discarded from a live equipment feed” |
| **Window construction** | After scaling is applied to the full dataframe, before regime segmentation; runs over the entire time-sorted, scaled dataframe | Segments the continuous scaled time series into fixed-size, non-overlapping windows of `WINDOW_ROWS = 120` rows (30 minutes at the configured 15-second sampling interval); a trailing partial window is dropped by default (`drop_incomplete=True`) | `WINDOW_ROWS = 120  # 30 minutes at 15-second intervals` (code comment) and `configs/default.yaml`: `window_rows: 120  # 30 minutes = 120 rows at 15-sec intervals` — establishes one fixed temporal unit that every later stage (regime clustering, cleaning, training, inference) consumes as its atomic sample | `n_windows = n_rows // window_size`; loop slices `values[start:end]` for contiguous, non-overlapping blocks of `window_size` rows; if `drop_incomplete` is False and rows remain, a final short window is appended instead of discarded. `construct_windows` (`preprocessing.py`, with the `WINDOW_ROWS` constant), core slicing loop `preprocessing.py`. `construct_windows_with_metadata` (`preprocessing.py`) attaches `start_time`/`end_time`/`window_id` per window | Feeding the autoencoder a variable-length trailing remainder would violate the model’s fixed 120-row input shape used at train and inference time. Failing to drop that incomplete tail by default would let a sparse partial window masquerade as a full 30-minute sample, understating its anomaly score relative to genuine full windows. Using a different or inconsistent window size across equipment would desynchronize the model architecture’s expected input dimension from what `fit_robust_scaler`/regime segmentation were calibrated against |

## 2. Regime Segmentation, Sensor Dropout & Transient Handling

| Step | When | What (feature) | Why it exists | How  | What if not |
| --- | --- | --- | --- | --- | --- |
| **Window feature computation** | Windows have been constructed from the scaled dataframe and regime segmentation is about to run | Collapses each window’s (window_size, n_sensors) array down to a single per-window feature vector — the column-wise mean over the configured load-indicator sensor columns — giving one row per window for clustering | KMeans needs one observation per window, not per timestep, and a window mean summarizes the operating level during that window rather than reacting to within-window noise | For each window, look up the column indices of `feature_columns` within `sensor_columns`, take `w[:, col_indices].mean(axis=0)`, and stack the results into a DataFrame with one row per window and one column per feature. `compute_window_features` (`regime.py`), called at `main.py` before `segment_regimes` | Clustering would have to run on raw per-timestep rows or an arbitrary flattening of each window, either exploding dimensionality per window or clustering individual readings instead of whole windows — breaking the assumption that a window belongs to a single regime |
| **Operating-regime segmentation (KMeans)** | `window_features` exist and at least one configured `regime.features` column (`speed`, `power`, `discharge_pressure`) is present in `sensor_columns` | Clusters windows into `regime.n_clusters` (default 3) groups using KMeans on the load-indicator feature means, then relabels clusters in ascending order of the first feature’s mean so label 0 is always lowest-load and n-1 highest-load | main.py comment: cluster “on configured load-indicator features (speed/power/discharge-pressure)” — equipment behaves differently at different load levels, so downstream per-regime cleaning/training needs windows binned by operating condition; the ascending relabel gives a stable, human-readable Low/Medium/High ordering instead of KMeans’ arbitrary cluster ids | `KMeans(n_clusters, random_state, n_init=10).fit_predict(X)` on `window_features[feature_columns].values`; cluster centers sorted by ascending first-feature mean and remapped via `label_map`; names come from `REGIME_LABELS = {0:"Low",1:"Medium",2:"High",3:"Transient"}`. `segment_regimes` (`regime.py`), invoked at `main.py` | All operating levels get treated as one population — a normal High-load reading looks anomalous relative to Low-load readings and vice versa, so per-regime cleaning/thresholding either over-flags legitimate load-driven variation or misses real anomalies hidden by the wider combined-regime spread. Without the ascending relabel, cluster index 0 could be the highest-load cluster on one run and lowest on the next (KMeans ids aren’t stable across fits), breaking anything downstream that assumes label ordering |
| **PCA fallback for unsupervised regime segmentation** | None of the configured `regime.features` exist in this equipment’s `sensor_columns` — `regime_features` is empty after filtering `configured_features` against `sensor_columns` | Reduces the per-window mean of the *entire* sensor set to `n_components` principal components via PCA, then runs the same ascending-order KMeans clustering on the reduced representation instead of named load columns | main.py comment: “If none of those are configured or present in this equipment’s sensor set, fall back to PCA on the full sensor set rather than guessing arbitrary columns” — a substitute load-proxy column would be fragile across different equipment’s sensor-naming conventions; PCA needs no domain knowledge of which column represents load | `window_means` = per-window mean across all sensors; `PCA(n_components).fit_transform(window_means)`; `KMeans` on the reduced components with the same ascending-order relabel by first-component mean. `segment_regimes_unsupervised` (`regime.py`), invoked at `main.py`, preceded by `logger.warning` at `main.py` | `segment_regimes` would be called with an empty `feature_columns` list — KMeans has nothing to cluster on — or, absent this fallback, the codebase would need to guess a substitute named column per equipment, silently clustering on a physically meaningless load proxy and mislabeling regimes as Low/Medium/High when nothing in the data actually corresponds to load |
| **Sensor-dropout window filtering** | Runs immediately after regime segmentation (either method) and before the per-regime cleaning pipeline | Flags and removes whole windows where too large a fraction of sensors are unreliable within that window — either NaN anywhere in the window, or “stuck” (max==min within `stuck_atol`) — against `preprocessing.sensor_dropout.threshold_pct` (default 5%); `regime_result.labels` is then filtered by the identical `keep_mask` so labels and windows stay index-aligned | Config comment: “Exclude window if >5% of sensors are null/stuck”; main.py comment: filtering “must run after regime segmentation but before per-regime cleaning, so the regime labels are filtered in lockstep with the windows they describe” — filtering independently or in the other order risks the windows array and the labels array drifting out of index sync | Per window: `is_null` = any NaN per sensor column; `is_stuck` = `(nanmax-nanmin) <= stuck_atol` per column; `bad_sensor_pct = n_bad/n_sensors*100`; `is_dropped = bad_sensor_pct > threshold_pct`. `detect_sensor_dropout_windows` (`sensor_dropout.py`). If any are dropped, main.py builds `keep_mask = ~is_dropped`, calls `remove_sensor_dropout_windows` (`sensor_dropout.py`), and applies the *same* `keep_mask` to `regime_result.labels` via `dataclasses.replace`, recomputing `window_counts` (`main.py`) | Windows with mostly-null or frozen sensors flow into per-regime cleaning and training looking like real (degenerate) data — near-zero reconstruction variance on those sensors gets learned as “normal,” masking genuine sensor failures at inference time. If `keep_mask` weren’t applied to `regime_result.labels` too, `windows[i]` and `labels[i]` would desync the moment any window is dropped, silently pairing every remaining window with the wrong regime for the rest of the pipeline |

## 3. Outlier Cleaning (per Regime)

| Step | When | What (feature) | Why it exists | How | What if not |
| --- | --- | --- | --- | --- | --- |
| **Per-regime cleaning** | After regime segmentation and the sensor-dropout filter, before any of the three outlier detectors run | Runs the isolation_forest → pca → mahalanobis sequence separately within each operating regime’s windows, then concatenates the results, instead of cleaning the whole window set as one distribution | A single global distribution mixes operating points (e.g. idle vs. full load); healthy low-load windows would look like statistical outliers next to a high-load majority (and vice versa), so fitting per regime keeps each detector’s “normal” baseline local to that regime — stated directly in the function docstring | `run_cleaning_pipeline` loops `regime_result.n_clusters`, masks `windows` per `regime_idx`, and re-runs the full detector sequence on `regime_windows` independently; a regime with fewer than 10 windows skips cleaning entirely and keeps all its windows (small-sample guard). `run_cleaning_pipeline` (`data/cleaning.py`) | A regime with legitimately different but internally-consistent sensor levels would have most of its windows flagged as global outliers and discarded, starving that regime in training and biasing the autoencoder toward the majority regime |
| **Isolation Forest** | First stage in the default order, before the covariance/PCA-based detectors | Flags windows whose per-window mean sensor vector is easy to isolate from the rest via random tree splits — a distribution-free, tree-based multivariate outlier flag | `contamination: 0.05` documents an expected ~5% gross-outlier rate to remove upfront, using a method that assumes nothing Gaussian or linear, before stages that do | Each window is collapsed to one feature vector (its per-sensor mean across all 120 rows); sklearn’s `IsolationForest` (n_estimators=200, contamination, random_state=42) is fit and predicts +1/-1 per window, -1 becomes `is_outlier`. `clean_isolation_forest` (`cleaning/isolation_forest.py`), `apply_isolation_forest` (`cleaning/isolation_forest.py`) | Gross non-linear multivariate outliers pass straight through to PCA/Mahalanobis, whose reconstruction-error and covariance estimates are then fit on contaminated data — weakening their thresholds against the very points they’re meant to catch (masking) |
| **PCA-space cleaning** | Second stage, after Isolation Forest has removed gross outliers, before Mahalanobis | Flags windows whose per-sensor mean profile doesn’t reconstruct well from a low-dimensional PCA basis — windows that break the normal correlation structure among sensors even without an individually extreme value | `variance_threshold: 0.95` keeps just enough components to explain the sensors’ shared operating structure; `outlier_std: 3.0` sets how far a window’s reconstruction error can sit above the mean before it’s judged inconsistent with that structure | Window means → full PCA to pick `n_components` via cumulative-variance search (`np.searchsorted`) → refit PCA at that dimensionality → `inverse_transform` back to sensor space → per-window MSE reconstruction error → outlier if error > mean + outlier_std·std. `clean_pca` (`cleaning/pca.py`, threshold `pca.py`), `apply_pca_cleaning` (`cleaning/pca.py`) | Windows with a plausible mean magnitude but an abnormal relationship between sensors (e.g. one rises while its normally-correlated partner stays flat) survive Isolation Forest’s isolation check and go undetected, left only to Mahalanobis’s coarser single-covariance-matrix version of the same idea |
| **Mahalanobis distance cleaning** | Third and final detector stage, run only after Isolation Forest and PCA have thinned the data | Flags windows whose mean sensor vector is statistically far from the regime’s multivariate mean, in covariance-normalized rather than raw Euclidean distance | `chi2_percentile: 97.5` sets the distance threshold from the chi-squared distribution at which a point is improbable under a multivariate-normal model; it runs last because “the covariance matrix estimate is more reliable on cleaner data” — Mahalanobis distance is itself sensitive to the outliers it’s trying to detect | Computes mean vector and covariance of window means, regularizes with `+1e-6·I`, inverts (falls back to pseudo-inverse on `LinAlgError`), computes `scipy.spatial.distance.mahalanobis` per window, threshold = `sqrt(chi2.ppf(chi2_percentile/100, df=n_features))`. `clean_mahalanobis` (`cleaning/mahalanobis.py`), `apply_mahalanobis_cleaning` | Run first or alone, still-present extreme outliers dominate the mean/covariance estimate, stretching the ellipsoid toward them and inflating the effective threshold — the exact masking failure the docstring warns about — so genuinely deviant windows score as within-threshold and pass uncaught |
| **Sequential composition of detectors** | Throughout each regime’s pass through `steps` (default `isolation_forest, pca, mahalanobis`) | The three detectors are not independent flags unioned together; each stage’s `apply_*` removes its flagged windows from `current` before the next stage runs, so each detector only ever sees the survivors of the ones before it | Cheaper, assumption-free filtering runs first so the covariance-sensitive Mahalanobis stage isn’t misled by outliers it would otherwise be diagnosing; `steps` is exposed as a parameter specifically so callers can reorder or subset stages for ablation studies without touching per-stage logic (`data/cleaning.py`) | Inside the per-regime loop, `current` is reassigned after each step; each stage’s flagged windows are appended to `all_rejected` before removal, so anything dropped ends up in `rejected_windows`; a step is skipped once fewer than 10 windows remain. `run_cleaning_pipeline` step loop (`data/cleaning.py`) | If the three ran independently against the original window set and results were unioned, PCA’s variance and Mahalanobis’s covariance would be computed on the full, still-contaminated data every time, reproducing the masking problem above; `test_reordered_steps_run_in_given_order` confirms a reordered `steps` gives a different audit trail |
| **Excessive-removal guard** | After all per-regime cleaning finishes, only if `output_dir` was passed to `run_cleaning_pipeline` | Compares total removal percentage against `max_removal_pct` (40%) and sets a logged warning plus an `excessive_removal` flag if exceeded | `max_removal_pct: 40` is commented “Warn if >40% of data removed overall” — a sanity check that cleaning parameters or genuinely poor data quality haven’t gutted the dataset before it reaches training | `validate_cleaning` computes `removal_pct = (1 - n_cleaned/n_original) * 100` and sets `excessive = removal_pct > max_removal_pct`, logging “Investigate data quality before training” when true; lands in `ValidationReport.excessive_removal`, renders as a red banner in the HTML report. `validate_cleaning` (`cleaning/validation.py`) | The guard is advisory only — it never stops the pipeline, reverts windows, or blocks training — so without it, or if `output_dir` is omitted (which skips validation entirely), a run that discards e.g. 90% of a regime’s data proceeds silently into training on an unrepresentative or too-small dataset |
| **Cleaning validation plots** | Once, after all regimes finish cleaning, only when `output_dir` is supplied | Generates before/after scatter plots for random sensor pairs, a histogram of post-cleaning per-window sensor means, and a bar chart of windows removed per step — visual diagnostics, not a schema/sanity check | Removal counts alone can’t show whether a detector removed a diffuse cloud of genuine outliers or carved a chunk out of a legitimate cluster; the plots let a reviewer visually confirm the cleaned distribution still looks like sensor data | `validate_cleaning` picks `n_sensor_pairs` (10 default) random, deterministically-seeded (`rng=42`) sensor-index pairs, plots each pair’s window-mean scatter before vs. after, plots a histogram of cleaned per-window means, and a bar chart of `per_step_removals`; PNGs saved under `output_dir`. `validate_cleaning` (`cleaning/validation.py`) | Cleaning and the excessive-removal check still run, but with no `output_dir` there is no visual evidence to catch a stage that quietly removed a legitimate sub-population rather than genuine outliers; the HTML report falls back to “No plots generated” |
| **Cleaning report generation** | After the full cleaning pipeline and its validation plots complete, before cleaned/rejected windows are saved to disk | Renders a self-contained HTML report: summary counts, a per-step-per-regime audit table, aggregate removals by method, a per-regime removal-percentage table, and embedded diagnostic plots | Gives a human-reviewable artifact of exactly how much data each detector removed and where, per equipment/run, rather than only transient log lines; `main.py` writes it unconditionally on every `step_clean` invocation | `generate_cleaning_report` builds HTML tables directly from `pipeline_result.step_logs`, `per_step_removals`, and `per_regime_results`, embeds each plot by filename, and prepends a red warning block when `excessive_removal` is set. `generate_cleaning_report` (`reporting/cleaning_report.py`), invoked at `main.py` | Per-step and per-regime removal counts still exist in `CleaningPipelineResult` and in log output, but nothing consolidates them into one artifact an engineer can open — diagnosing why a regime lost most of its windows would require re-deriving it from raw logs or code |

## 4. Model Architecture & Training

| Step | When | What (feature) | Why it exists | How | What if not |
| --- | --- | --- | --- | --- | --- |
| **Regime-stratified train/val/test split** | Right after cleaning, before any model code runs | Splits windows into train/val/test at window boundaries, slicing each regime’s windows contiguously before concatenating, instead of one contiguous cut over the whole list | `run_cleaning_pipeline` returns windows ordered by regime; a single contiguous split would put validation/test entirely inside whichever regime(s) fall at the tail | Per regime, take the first `train_pct` windows as train, next `val_pct` as val, remainder as test, then concatenate across regimes. `split_windows` (`training/dataset.py`). Falls back to one plain contiguous cut when `regime_labels` is omitted | Val/test end up sampled from only the tail regime(s); calibration and reported metrics look fine but don’t reflect the equipment’s other operating regimes — `step_train` logs an explicit warning when `regime_labels` is `None` (`main.py`) precisely because this was seen as a risk |
| **Latent-dimension selection (PCA) / manual override** | Once train windows exist, before building the model | Picks how many neurons the bottleneck has, i.e. how many independent modes of “normal” behaviour the autoencoder is allowed to represent | An arbitrary fraction of sensor count is not grounded in the data; intrinsic dimensionality should come from how much of the sensors’ actual variance is truly independent | Fits PCA on scaled training rows, takes the cumulative explained-variance-ratio curve, returns the smallest component count reaching `variance_threshold` (default 0.95), floored at `floor` (default 4). `pick_latent_dim` (`model/architecture.py`); `model.latent_dim` can be set explicitly to skip PCA (`configs/default.yaml`, wired in `main.py`) | Too large a bottleneck: the network can nearly copy input to output, defeating the reconstruction-error anomaly signal. Too small (unfloored, e.g. rank-1 degenerate sensors): the network can’t represent normal variation, inflating baseline error everywhere and swamping real anomalies in noise |
| **LayerNorm chosen over BatchNorm** | Applied inside every hidden layer of the encoder/decoder, every forward pass | Normalizes activations across sensors within a single row rather than across a batch | Each gradient-update batch is a single 30-minute window: its 120 rows are highly autocorrelated steady-state samples, so a batch’s own mean/variance is a poor, noisy stand-in for the sensor’s true global spread | Every hidden layer is `Linear -> LayerNorm -> ReLU -> Dropout`; LayerNorm normalizes per-row across sensors, no dependence on how windows are batched. `architecture.py`, rationale in the `Autoencoder` docstring; config records the choice: `norm: "layer"` (`configs/default.yaml`) | BatchNorm would normalize by that tiny, noisy per-window variance, injecting unstable scaling into every training step — training destabilizes or fails to converge because the “batch statistics” don’t represent the sensors’ real operating range |
| **Automatic early-stopping patience derivation** | While assembling `TrainConfig`, after hidden widths (and thus depth) are known | Picks how many non-improving epochs to tolerate before stopping, scaled to network depth, while guaranteeing the LR scheduler always gets to act first | Deeper architectures need proportionally more epochs to find a good basin; but patience must stay above `lr_patience` or early stopping can fire before `ReduceLROnPlateau` ever reduces the LR | `patience = lr_patience + patience_per_hidden_layer * (n_hidden_layers + 1)` when not set explicitly. `step_train` (`main.py`) | Verified failure mode: at a flat `patience=5` with `lr_patience=10`, early stopping fired before `ReduceLROnPlateau` ever got a chance to act, for every config — silently disabling the LR scheduler entirely |
| **Row-shuffled batching**  | Inside every training epoch, before iterating batches | Shuffles all rows across all training windows, then batches by `batch_size` rows, instead of treating each window as one gradient step | Windows are stored contiguously by regime; a literal one-window-per-step loop feeds long unshuffled runs of single-regime, highly autocorrelated rows into each step | `rows = windows.reshape(-1, n_sensors)`, `np.random.permutation(n_rows)`, iterate `batch_size`-row slices of the permuted index. `train_one_epoch` (`training/trainer.py`); `batch_size_rows: 256` in config records the deviation | Verified empirically to prevent convergence on this data regardless of model normalization — training window-per-step plateaued far above a trivial constant-prediction baseline, because each step’s gradient came from one long run of near-identical, single-regime rows |
| **Overfit-ratio warning (val/train loss ratio)** | Every epoch during training, and again once on the restored best epoch | Surfaces overfitting as it happens instead of only being visible after the fact in saved loss curves | Needs an operator-visible signal distinct from raw loss numbers, since a falling val_loss can still be badly disproportionate to train_loss | Computes `val_train_ratio = val_loss / train_loss` each epoch, logs a warning whenever it exceeds `overfit_ratio_threshold` (default 1.5). `train_model` (`training/trainer.py`); `step_train` repeats the check on the restored best epoch (`main.py`) | Without it, overfitting shows up only as a number quietly sitting in `history["val_train_ratio"]` that nobody inspects — the ratio spikes from the weight_decay incident would have gone unnoticed until thresholds/alerts already misbehaved downstream |
| **Sensor baseline computation from the test split** | After training and threshold calibration, using the held-out test windows | Computes a per-sensor mean-MSE reference used at inference time to normalize live error into “how much worse than normal” ratios per sensor | Needs an unbiased, never-seen-during-training-or-calibration reference; using train or val data would understate true normal error | Runs the trained (eval-mode) model over every test window, computes `per_sensor_mse` per window, averages across windows to get one baseline value per sensor. `compute_sensor_baselines` (`training/trainer.py`); invoked only `if test_arr is not None and len(test_arr) > 0` (`main.py`) | If test windows are unavailable, baselines are skipped (`sensor_baselines = None`) and downstream inference loses the per-sensor normalized ratio entirely. If baselines were instead computed from train/val data, they’d be optimistically low, making live sensor error ratios look inflated and causing false positives at alerting |
| **Hyperparameter grid search** | Optional, offline — run separately from the main `step_train` path before committing to a config | Searches combinations of `latent_dim`, `learning_rate`, and `dropout` to find the config with the best validation performance, rather than relying solely on the PCA heuristic and config defaults | Not stated in code; distinct utility module, not wired into `main.py`’s pipeline | Builds the Cartesian product of `latent_dims x learning_rates x dropouts` (defaults `[8,12,16] x [1e-3,5e-4] x [0.1,0.2]`), runs `train_model` for each with a shorter `max_epochs`/`patience`, compares trials by each trial’s own restored `history["best_val_loss"]`. `grid_search` (`training/hyperparams.py`) | Without it, architecture/optimizer hyperparameters come only from the PCA heuristic plus fixed config values, with no empirical comparison across alternatives; comparing trials by last-epoch loss instead of best-restored loss would make a trial that stopped early or late look artificially worse/better independent of its actual quality |

## 5. Threshold Calibration

| Step | When | What (feature) | Why it exists | How | What if not |
| --- | --- | --- | --- | --- | --- |
| **Robust threshold estimation (median + z·MAD/IQR on log-score)** | Default path of `compute_thresholds` (`method="robust"`, the config default) | Log-transforms window scores, then sets threshold = `median + z(percentile)·scale` in log-space (scale from MAD or IQR), exponentiated back to score units | Reconstruction-error scores are non-negative and right-skewed, not symmetric, so log(score) approximates a normal bulk far better than raw score. Reading the percentile off `median + spread` uses the bulk of the distribution instead of the noisy tail itself; z(p) is the standard-normal quantile — ~1.28 for P90, ~2.33 for P99 | `_log_transform` (`thresholds.py`) clips non-positive scores to `np.finfo(np.float64).tiny` before `log`. `_robust_log_threshold` computes `z = norm.ppf(percentile/100)`, then `median + z·1.4826·MAD` (spread=“mad”) or the IQR-equivalent. `compute_thresholds` exponentiates back | Falls back to the noisier plain-percentile method. If the log-normal-bulk assumption is badly violated and never cross-checked against the percentile method (a check the docstring itself recommends), the robust threshold can land far from the true empirical percentile it’s meant to approximate |
| **Window-level score aggregation (P95 of per-row errors)** | Every time a window’s 120 per-row MSE values are collapsed into one anomaly score — both during calibration and at inference | Aggregates the 120 per-row errors in a window into a single scalar via the 95th percentile, so one bad row isn’t averaged away but a single spike also can’t dominate the way a `max()` would | To capture the the severity of a window’s anomalies without letting a singular anomaly dominate the metric completely. | `window_anomaly_score` (`model/loss.py`) hardcodes `float(np.percentile(row_errors, 95))`; called from `compute_training_errors` (`main.py`) and from `inference/pipeline.py`. Note: `thresholds.score_aggregation: "p95"` in config is never actually read by any code (confirmed by repo-wide grep) — it documents current behaviour but is not a live switch | With mean aggregation, a single row stuck at an extreme value for 15s inside a 30-minute window gets diluted by the other 119 normal rows and never crosses into Yellow/Red. With max aggregation, one noisy row causes chronic false Yellow/Red flags. Separately: editing `score_aggregation` in a config file today has zero effect, since the aggregation is hardcoded in `loss.py` |

## 6. Inference Pipeline (per Window)

| Step | When | What (feature) | Why it exists | How | What if not |
| --- | --- | --- | --- | --- | --- |
| **Forward-fill short gaps** | Every inference window before scoring, when it contains any NaNs | Per-sensor forward-fill of NaN runs up to `max_consecutive_nulls` (default 3) readings, carrying the last valid reading forward | Short, isolated sensor dropouts (a missed poll, a transient comms blip) shouldn’t sink an otherwise-good window; forward-fill is the cheapest defensible guess for a brief gap | `forward_fill` (`inference/missing_data.py`) walks each column tracking a `last_valid` value and a `consecutive` counter, filling while `consecutive <= max_consecutive` and a valid value has been seen; longer runs, or a column starting with NaN, are left as NaN (`unfillable`) | A gap of 4+ consecutive nulls in a sensor would either propagate NaN into the model (poisoning every reconstructed output through the Linear layers) or, if filled anyway, fabricate up to minutes of flat synthetic signal that reads as “no change” regardless of what’s actually happening |
| **Per-sensor null-dominance flagging** | After forward-fill, per sensor, within `assess_window_quality` | Marks a sensor “null-dominant” for this window if its *raw* null % (before fill) exceeds `max_null_pct_per_sensor` (default 5%), or if forward-fill still left it with unfillable NaNs | A sensor can be “fillable” (every gap ≤3 rows) yet still be mostly fabricated if those gaps recur throughout the window — raw null % catches that case that “still has NaN after fill” alone would miss | `assess_window_quality` (`missing_data.py`) takes the union of `bad_pct_sensors` (from `check_nulls`) and `still_null_sensors` into `null_dominant_sensors` | Without the raw-% check, a sensor with e.g. 15 separate 2-row gaps (30% null but each gap individually fillable) would be scored as if fully real, letting a mostly-fabricated signal silently drive the reconstruction error and diagnosis |
| **Window-level accept/reject on null-dominant sensors** | Once per window, after per-sensor null-dominance is computed | Rejects the whole window only if the *fraction of all sensors* that are null-dominant exceeds `max_null_dominant_sensor_pct` (default 5%); below that, the window is kept with just those sensors masked | Deliberately mirrors `preprocessing.sensor_dropout.threshold_pct` — the config comment states it “matches … same bar used at training time” — so the model isn’t asked to judge windows worse than anything it was trained on | `assess_window_quality` (`missing_data.py`): `null_dominant_pct = len(null_dominant_sensors) / n_sensors * 100`; over threshold returns `usable=False`; otherwise `usable=True` with `masked_sensors`. `infer_window` (`pipeline.py`) short-circuits to `_not_usable_result` | Without this symmetry, inference could silently score windows with far more corrupted sensors than the model ever saw at training time, or reject far more real operating windows than necessary, undermining the calibration between training-time and inference-time data quality |
| **Neutralizing masked sensors before the forward pass** | Every window with `masked_sensors`, after scaling, before the model call | Overwrites the masked sensors’ scaled values with 0.0 (the RobustScaler’s median) instead of leaving unfillable NaNs or fabricated fills | An Autoencoder’s Linear layers mix every input column together, so leaving NaN in even one masked column would poison every reconstructed output, not just that sensor’s; zero-at-median is a neutral, config-invariant stand-in | `infer_window` (`pipeline.py`): `scaled[:, masked_sensors] = 0.0` after `scaler.transform` + `apply_tail_compression`, guarded by `if masked_sensors:` | Passing NaN straight into `model(x)` would produce NaN throughout `x_hat` via matrix multiplication, silently NaN-ing out the score and diagnosis for the entire window instead of just the bad sensor |
| **Excluding masked sensors from the window score** | Every window with `masked_sensors`, at error computation | `row_errors` (which feed the window score) are computed only over non-masked columns; `sensor_errors` still cover all columns but masked ones are zeroed before ranking/summing | A masked sensor’s reconstruction reflects an artificial neutral input, not real signal — including it would dilute or inflate every row’s error regardless of the equipment’s actual state | `infer_window` (`pipeline.py`): boolean `keep` mask over columns, `row_errors = per_row_mse(x[:, keep], x_hat[:, keep])`; `sensor_errors = per_sensor_mse(x, x_hat)` still computed over all columns | Including a masked, artificially-flat sensor’s near-zero reconstruction error would drag down the P95 window score (masking a real anomaly elsewhere), or its artificially divergent error would falsely inflate the score |
| **Usable vs. unusable result and forcing unusable windows to green** | Whenever equipment isn’t running, or the window is null-dominant-rejected | An unusable window returns `usable=False` with NaN score/errors/reconstruction and no diagnosis, via `_not_usable_result`; `step_infer` then forces its zone to `"green"` rather than calling `classify_zone` | An anomaly score can’t be trusted from data the pipeline couldn’t clean or from equipment that wasn’t even running, so the pipeline fails safe to “no alert” instead of guessing; per the `main.py` comment, “unusable windows don’t trigger alerts” | `_not_usable_result` (`pipeline.py`) fills every numeric field with NaN and sets `usable=False`; called at the running-check and null-dominant-reject exit points; `step_infer` (`main.py`) forces `zone="green"` when `not result.usable` | Forcing red instead would raise false alerts every time data quality glitches or the equipment is simply shut down, training operators to distrust/ignore the alerting system; scoring the NaN-filled result through `classify_zone` directly would crash or non-deterministically classify on NaN comparisons |
| **Sensor-level diagnosis: heuristic MSE-share ranking** | Every usable window, to produce `top_contributors` | Ranks sensors by their share of total reconstruction error, returning the top-K with index, name, error, and contribution % | Operators need to know *which* sensors are driving an anomaly, not just that one occurred. This heuristic is the only attribution method in the codebase — an earlier FastSHAP / Integrated Gradients implementation existed and was removed; nothing pluggable remains here | `diagnose_window` (`inference/diagnosis.py`): `sensor_errors = per_sensor_mse(x, x_hat)`; masked sensors zeroed in a copy before `total_error = ranking_errors.sum()`; `sensor_contributions` (`model/loss.py`) sorts by `error/total*100` descending | Without zeroing masked sensors first, an artificially flat (or divergent) masked sensor could be reported as the “top contributor” for an anomaly it never actually exhibited, misdirecting an operator’s investigation |
| **Ratio-based sensor flags (`sensor_flag_threshold`, `anomaly_sensor_pct`)** | Every usable window where `sensor_baselines` is supplied | Normalizes each sensor’s error against its own historical baseline (`error_ratios = sensor_errors / baselines`), flags a sensor when the ratio exceeds `flag_threshold` (default 3.0), and declares the whole window `sensors_anomalous` when the flagged fraction exceeds `anomaly_sensor_pct` (default 10.0%) | Raw MSE share only tells relative contribution *within* a window; a ratio against each sensor’s own baseline distinguishes “unusually bad for this sensor” from “this sensor is naturally noisier than others,” giving a window-wide anomaly verdict independent of the P95 score | `diagnose_window`: `safe_baselines = np.where(baselines > 0, baselines, 1e-10)` guards divide-by-zero; `sensor_flags = (error_ratios > flag_threshold)`; masked sensors forced un-flagged and excluded from `n_scored` before `pct_flagged`; `sensors_anomalous = pct_flagged > anomaly_sensor_pct` | Without the `1e-10` floor, any sensor with a zero baseline would divide by zero and produce NaN/inf ratios; without excluding masked sensors from `n_scored`, a masked sensor’s forced-0 flag would deflate `pct_flagged` and could mask a real `sensors_anomalous` verdict |

## 7. Alerting (Zones, Persistence, Episodes)

| Step | When | What (feature) | Why it exists | How | What if not |
| --- | --- | --- | --- | --- | --- |
| **Zone classification** | After each window’s anomaly score (P95 of per-row MSE) is computed, before any persistence/alert logic runs | Maps a window’s continuous anomaly score to a discrete Green/Yellow/Red zone using the calibrated `green_yellow`/`yellow_red` thresholds | Persistence rules operate on discrete states, not raw scores, so a categorical label is needed as the hand-off between scoring and alerting | `score >= yellow_red` → red; `elif score >= green_yellow` → yellow; else green (both boundaries inclusive on the higher side). `classify_zone` (`alerting/zones.py`), batch wrapper `classify_batch`. Called per-window in `step_infer` (`main.py`); an unusable window is forced to `"green"` instead of classified (`main.py`) so it can’t pollute the persistence history | No discretization means persistence’s consecutive-window counters have nothing consistent to count; an unusable/rejected window would either be silently dropped (breaking the consecutive-run count) or wrongly scored, corrupting the zone history that everything downstream depends on |
| **Persistence: consecutive-red escalation** | Every time a new window’s zone is appended to the history, evaluated first (“most severe first”) before any other persistence rule | Requires 2 consecutive Red windows to raise a Yellow alert, and 3+ consecutive Red to raise a full Red alert — a single Red window alone raises nothing | Config: `red_to_yellow_alert: 2 # 2 consecutive Red → Yellow alert`, `red_to_red_alert: 3 # 3+ consecutive Red → Red alert`; module docstring: “require consecutive anomalous windows before raising alerts” | `apply_persistence` counts trailing consecutive `"red"` entries walking `zone_history` in reverse, stopping at the first non-red (`persistence.py`); `>= red_to_red_alert` → red; `elif >= red_to_yellow_alert` → yellow. Streaming twin `compute_alert_level_timeline` tracks the same counter incrementally. Verified by `test_single_red_no_alert`, `test_two_reds_yellow_alert`, `test_three_reds_red_alert` | A single noisy Red window would page on-call every time with no smoothing — alert fatigue on transient blips. Without the 3-red red-tier, a real sustained fault (3+ windows) would be capped at the same Yellow severity as a 2-window blip, under-escalating a genuine ongoing failure |
| **Persistence: sustained-yellow escalation** | Checked only after the red-tier check fails (`consecutive_red < red_to_yellow_alert`), each time the history grows | 4+ consecutive Yellow windows (with zero trailing Red) raise a Yellow alert even though Red was never reached | Config: `yellow_consecutive: 4 # 4+ consecutive Yellow → Yellow alert` | `consecutive_yellow` only counted when `consecutive_red == 0` (`persistence.py`); `>= yellow_consecutive` → yellow. `test_three_yellows_no_alert` confirms 3-in-a-row is still Green, `test_four_yellows_yellow_alert` confirms 4-in-a-row trips Yellow | A sensor that drifts into borderline (Yellow) territory and plateaus there — a slow, chronic degradation that never quite crosses into Red — would never alert at all, a missed detection of exactly the kind of gradual-onset fault the Yellow band exists to catch |
| **Persistence: mixed Red+Yellow within trailing window** | Only active when `mixed_window_hours` is configured (>0); checked last, after both red-tier and pure-yellow-streak checks fail | Looks at every Red/Yellow window (not just consecutive runs) inside a trailing span of `mixed_window_hours` (2h → 4 windows) and raises Yellow if the weighted mix `2*red_count + yellow_count >= 4`, requiring at least one window of each color | Extends coverage to “interleaved patterns” (e.g. red-green-yellow-green-red oscillation) that the pure consecutive-run rules structurally can’t see, using “the same threshold that a pure 2-red or pure 4-yellow streak already hits on its own” (`persistence.py`) | `trailing_span = zone_history[-lookback_windows:]`; counts within that span; trigger is `mixed_red_count>=1 and mixed_yellow_count>=1 and (2*mixed_red_count+mixed_yellow_count)>=4`; by construction can never escalate to Red — only the earlier-checked 3-consecutive-red rule can (`test_never_escalates_past_yellow`, `test_consecutive_red_rule_still_wins_over_mixed`) | An oscillating fault — red, green, yellow, green, red — never forms 2 consecutive reds or 4 consecutive yellows, so without this rule it sits at Green/no-alert despite genuine instability across a ~2h span (`test_disabled_by_default` shows this is exactly what happens when the rule is off) |
| **Episode grouping** | After a full per-window alert-level timeline exists, for reporting and evaluation rather than for making the live alert decision itself | Collapses a per-window alert-level array into episode records — a maximal contiguous run of non-Green windows becomes one record with start/end window index, start/end timestamp, `peak_level` reached, and `n_windows` | Episodes are “the actual client-facing alert unit referenced throughout the evaluation plan” (`alerting/episodes.py`) — dashboards and precision/recall metrics should count one multi-hour event, not every window in it | `extract_episodes` scans `alert_levels`, skipping Green (`episodes.py`); on the first non-Green opens an episode and extends it while non-Green, tracking the worst level via `_SEVERITY = {"green":0,"yellow":1,"red":2}`; closes at the next Green or end of array. `extract_episodes` (`episodes.py`) — purely a post-hoc grouping transform, introduces no new thresholds (`test_multiple_separate_episodes`, `test_episode_covering_entire_timeline`) | Without grouping, a single 6-hour Red episode spanning 12 windows is reported/counted as 12 independent alert events — evaluation metrics get computed on the wrong unit, and any dashboard shows a flood of per-window alerts instead of one coherent incident with a clear start, end, and peak severity |

## 8. Monitoring (Drift, Health Log, Retrain Triggers)

*Every step in this section exists as tested, working code in `src/autoencoder/monitoring/`, but a repo-wide grep confirms none of it is imported by `main.py` or any `scripts/*.py` — it is a standalone/library-only capability, not (yet) wired into the documented CLI pipeline.*

| Step | When | What (feature) | Why it exists | How | What if not |
| --- | --- | --- | --- | --- | --- |
| **Weekly health logging** | Would run periodically (e.g. weekly cron) consuming daily scores/zones produced by the live inference path | Aggregates a week of daily anomaly scores and zone labels per equipment unit into mean/max/min/std, per-zone day counts, and an alert rate, then appends the result as one JSON line to a per-equipment log file | Gives a persistent, appendable longitudinal record of equipment condition so trend/drift checks (which need history) have something to read | `compute_weekly_metrics` computes `zone_counts` and `alert_rate = (yellow+red)/total`; `log_weekly_health` appends `{equipment_id, week_start, logged_at, **metrics}` to `{log_dir}/{equipment_id}_health.jsonl`; `read_health_log` replays it. `health_log.py` | No persistent weekly record exists anywhere else in the codebase, so an analyst can’t answer “was this pump degrading over the last two months” without re-deriving it from raw score streams; drift/retrain functions take `daily_errors`/`recent_errors` as plain inputs with no producer of that history without this log |
| **Rolling-trend drift check** | Would consume the accumulating `daily_errors` history over `rolling_error_window_days` (7-day) | Smooths daily error scores with a 7-day rolling mean, then linear-regresses the smoothed series to flag a statistically significant (p<0.05) upward slope | Day-to-day noise makes single-day error comparisons unreliable, so a slow degradation trend needs to be seen across a smoothed window and confirmed by regression significance rather than one bad day | `rolling_error_trend(daily_errors, window_days=7)` convolves the series with a `1/window_days` kernel (mode=“valid”), runs `scipy.stats.linregress`; `is_increasing = slope > 0 and p_value < 0.05`; returns early if fewer than `window_days` points exist. `drift.py` | A gradual creep — e.g. a bearing slowly wearing — never crosses any single-day threshold and would never register; since this is the only slope-based check feeding `check_retrain_needed`, that failure mode is invisible to the trend trigger entirely (though the separate KS-test could still catch a large-enough shift) |
| **KS-test distribution-shift drift check** | Would compare a stored baseline error distribution against a recent window’s distribution | Runs a two-sample Kolmogorov-Smirnov test globally, and optionally per sensor, to detect that the *shape* of the error distribution has shifted, not just its trend, and to localize which sensor is responsible | Catches sudden/structural shifts (a recalibration, part swap, process change) that a slope-based trend check would miss, and the per-sensor variant tells an operator which sensor rather than just “something changed” | `ks_test_drift(baseline_errors, recent_errors, significance)` runs `scipy.stats.ks_2samp`, flags `is_drifted = p_value < significance` (default 0.01); `per_sensor_drift` loops per column calling `ks_test_drift` per sensor and sorts descending by KS statistic. `drift.py` | A sudden distribution shift with no gradual buildup is only caught here (or not at all, if too small/short for the sample size). Separately: `ks_test_min_sensors=5` from config is never read anywhere in the code, so `per_sensor_drift` runs with no minimum-sensor-count guard and can report spurious per-sensor “drift” on a tiny, low-power sensor set |
| **Retrain-trigger orchestration** | Weekly cadence | Combines the trend check, the KS-test drift check, and a false-alarm-rate check (current fraction of recent errors above baseline’s P90, vs. that same fraction in baseline scaled by `false_alarm_rate_multiplier`) into one `retrain_recommended` boolean with a human-readable `reasons` list | Each targets a different failure mode (gradual drift, sudden shift, alarm fatigue), so requiring only one to fire avoids needing all three to co-occur before acting | `check_retrain_needed` requires `trend["is_increasing"]` AND `n_days >= drift_weeks_threshold*7` for the trend reason; calls `ks_test_drift` for the shift reason; flags false-alarm-rate if `current_false_alarm_rate > baseline_false_alarm_rate * false_alarm_rate_multiplier`; `retrain_recommended = len(reasons) > 0`. `retrain_triggers.py` | The individual signals from `drift.py` remain just numbers nobody consumes — there is no single decision point for “retrain now,” and since the whole `monitoring` package is never imported by `main.py` or `scripts/`, no retrain decision is ever made automatically anywhere in the current codebase; a model can silently drift indefinitely, retraining depending entirely on someone manually re-running `train.py` |

## 9. Offline Evaluation (Ground Truth & Slug Metrics)

| Step | When | What (feature) | Why it exists | How | What if not |
| --- | --- | --- | --- | --- | --- |
| **Ground-truth window aggregation** | When `evaluate_against_labels.py` loads a `*_equipment_combined.parquet` file, once per run, before any per-slug metric is computed | Chunks the raw 15-second-granularity rule-firing export into the same fixed-size (120-row) windows the model itself scores, aggregating each window’s is_anomaly/n_active_events/max_event_level by max and the list-valued columns (rule slugs, sensors) by set union | “aligned 1:1 by window_id with a model’s own window scores computed from the same file at the same window_size — both are a deterministic function of (file, window_size), so joining on window_id (not a timestamp match) is safe” (`WindowGroundTruth` docstring) | `load_window_ground_truth` (`evaluation/ground_truth.py`) groups raw rows by window_id, taking `.max()` for scalar columns and `_union_of_arrays` for list-valued ones; drops the trailing incomplete window (same convention as `construct_windows_with_metadata`) | Per-row ground truth and per-window model scores would have no common index to compare; joining by timestamp instead risks off-by-one misalignment if either side’s windowing convention drifts, silently corrupting every downstream metric |
| **Catalog-based sensor deconfounding** | When `--rule-to-sensors` is passed, overriding whatever `all_triggering_sensors` column the file has | Derives each window’s ground-truth sensor set from the union of every active rule’s own static sensor list (optionally scoped to `valid_sensors`), instead of the file’s own `all_triggering_sensors` column | “the catalog attributes each active rule to exactly its own sensors, while the column (a union across every concurrently-active rule) is confounded the moment more than one rule fires at once”; `valid_sensors` exists because “the catalog is plant-wide … without this filter the ground truth for one equipment gets polluted with dozens of unrelated other-equipment sensor names, inflating the Jaccard-overlap denominator” | `expand_sensors` (`ground_truth.py`) unions `rule_to_sensors.get(rule, [])` over a window’s rule_slugs then intersects with `valid_sensors`; called per window in `load_window_ground_truth`, and again per-slug in `build_slug_row` (`scripts/evaluate_against_labels.py`) | With concurrent rules, every window’s ground-truth sensor set becomes a blob of every co-firing rule’s sensors, so a model correctly attributing only its own rule’s sensors would score a low Jaccard purely from unrelated co-firing rules, and an unscoped plant-wide catalog crushes the score further with irrelevant other-equipment sensor names |
| **Pointwise slug metrics** | Inside `build_slug_row`, for each slug, once window scores and ground truth are aligned | Confusion-matrix precision/recall/F1 of (zone != green) against the slug’s binary presence series, plus PR-AUC of the continuous anomaly_score, restricted to usable windows | “Valid whether the slug covers 20 windows or 20,000 windows — no minimum count required” (`slug_metrics.py`) | `pointwise_metrics` (`slug_metrics.py`) masks both series by the `usable` flag, computes `confusion_matrix` for precision/recall/F1 and `average_precision_score` for PR-AUC, guarded to NaN when the masked set has only one class or all-NaN scores | Without the usable mask, windows already rejected upstream for missing/bad sensor data would be scored as if the model made a real green/non-green decision on them; without the single-class guard, PR-AUC would raise or silently return a meaningless value on a slug that never fires |
| **Episode descriptive stats** | Inside `build_slug_row`, alongside pointwise metrics, for each slug | Episode count and min/median/max duration for one slug’s binary presence series, reusing the same episode-extraction logic as live alerting | “Purely descriptive — not used to branch any downstream logic, just reported so a reader can tell ‘rare short fault’ from ‘persistent regime shift’ without the code itself encoding that judgement” (`slug_metrics.py`) | `episode_stats` (`slug_metrics.py`) turns the binary series into green/red labels and calls `extract_episodes` (`alerting/episodes.py`) — the same function the live persistence/alerting path uses — then reports the sorted duration distribution | Pointwise precision/recall/F1 alone cannot distinguish a single fault spanning 200 consecutive windows from 200 separate one-window blips with the same total active-window count, so a reader can’t tell whether low recall means “missed one long fault” or “missed 200 short ones” |
| **Episode-level false-alarm rate** | Once per run, after all per-slug rows are built, using the model’s own persistence-suppressed alert timeline rather than raw per-window zones | For each model alert episode (a contiguous Yellow/Red run), checks whether it overlaps any_slug activity anywhere in its window range; non-overlapping episodes are further checked against every known slug’s aggregate sensor signature and flagged if they closely resemble one | The `Episode` dataclass is “the actual client-facing alert unit referenced throughout the evaluation plan”; resembling episodes are “reported separately, never folded silently into the false-alarm rate” (`scripts/evaluate_against_labels.py`) | `episode_false_alarm_rate` (`scripts/evaluate_against_labels.py`) builds model episodes via `extract_episodes` on `compute_alert_level_timeline`’s output, flags an episode false if no window in its range has any_slug active, then for false episodes computes Jaccard between the episode’s unioned top_sensors and each known slug’s signature; `window_false_alarm_rate` reports the raw per-window equivalent for comparison | Counting false alarms per raw window instead would count one long false-alarm episode the same as dozens of separate short ones, misrepresenting how many distinct alerts an operator actually has to triage; without the resemblance check, a real early/leading detection of a not-yet-fired rule would be indistinguishable from genuine noise in the false-alarm rate |
| **Concurrency-split sensor attribution** | Inside `build_slug_row`, for each slug, after detected+usable windows are identified | Sensor-attribution Jaccard overlap and top-k hit rnoate between the model’s attributed sensors and ground-truth sensors, split into low/high concurrency buckets by n_active_events at the time | “so the report makes clear whether attribution quality is being measured on clean or confounded instances” (`slug_metrics.py`) | `sensor_attribution_metrics` (`slug_metrics.py`) computes Jaccard/top-k hit rate over already-filtered eligible windows (detected AND usable), skipping windows with empty ground-truth sensor sets; `sensor_attribution_by_concurrency` partitions those windows by whether n_active_events is at or below `--concurrency-threshold` | A single blended attribution score would hide whether poor sensor attribution comes from genuinely bad model behavior or from an unavoidable confound (multiple rules firing on overlapping sensors at once), so a model could look mediocre overall while actually being excellent on clean instances and only failing on inherently ambiguous concurrent ones |
